# 阶段 3：上下文压缩

> 目标：长对话不爆上下文窗口，agent 能持续对话而不丢失关键信息

---

## 为什么需要这个？

DeepSeek 上下文窗口是 128K tokens。理论上能聊很久，但实际上：

1. **Token 是钱**：每轮对话都把全部历史发给模型，越聊越贵
2. **模型注意力稀释**：历史太长，模型对早期指令的注意力下降
3. **没有压缩 = 只能靠重启**：超过窗口后对话直接失败

## 技术选型对比

### 四个框架的压缩策略

| 框架 | 触发条件 | 压缩方式 | 复杂度 | 适合初学者？ |
|------|---------|---------|--------|------------|
| **CC** | 距窗口上限 13K token 时 | "PTL 剥洋葱"——从最早消息逐层剥离，SM 直挂免重摘要 | 高 | ❌ 太复杂 |
| **tinypace** | 使用量 92% 时（阈值比 = 0.92） | 两阶段：Phase1 压缩旧历史 + Phase2 压缩当前轮 | 高（728行） | ❌ 耦合太重 |
| **Hermes** | ContextEngine 自行决定 | 结构化摘要模板，cheap 模型做摘要 | 中 | 🔸 |
| **OpenCLAW** | 硬下限 16K + 预警 32K | 三级恢复：压缩 → 截断 → 报错 | 最高 | ❌ 过度设计 |

### 选型结论：提取 tinypace 核心模式，简化到 ~120 行

**为什么不能直接抄 tinypace 的 `auto_compact.py`（728行）？**

tinypace 的压缩模块是一个"完整的集成系统"，不是独立功能：
- 依赖 `SessionState` 做长期记忆存储
- 依赖 `FileRecoveryManager` 做压缩后文件恢复
- 依赖 `MessageNormalizer` 做消息预处理
- 依赖 `tiktoken` 做精确 token 计数
- 依赖 `context_retrieval_service` 做记忆索引

如果直接抄，需要把整个 tinypace 的 session/state/memory 体系都搬过来。**提取核心逻辑、去掉耦合，比整体搬运更快。**

**要保留什么（tinypace 的精髓）？**

```
1. 阈值触发机制：token 数超过窗口的 N% 时触发
2. Head/Tail 分割：找到最后一条用户消息，之前的是 Head（可压缩），之后的是 Tail（保留）
3. LLM 摘要 Head：调模型把旧对话压缩成摘要
4. 摘要替换历史：用摘要消息替换原始旧消息
```

**要简化掉什么？**

| 删除的部分 | 理由 |
|-----------|------|
| tiktoken 依赖 | 用简单估算：`len(str(msg)) / 4 ≈ tokens`，误差 20% 但够用 |
| FileRecoveryManager | 暂时没有"压缩后恢复最近打开文件"的需求 |
| Phase 2 Tail 压缩 | 当前轮（Tail）先不压，只压历史（Head） |
| Memory 索引 | 记忆搜索是阶段 4 的事 |
| 两场景 fallback | 简化为：如果压完还是太大，直接截断最早的消息 |

**要借鉴 OpenCLAW 的什么？**

从对比文档分析，OpenCLAW 有一个关键设计值得借鉴：

> **压缩前记忆刷新**：压缩前先把当前关键信息写入 MEMORY.md

这就避免了"压缩把重要信息压没了"的问题。我们可以在压缩前调一次 memory 写入。

**要借鉴 CC 的什么？**

> **熔断器**：连续压缩失败 N 次后停止尝试，避免无限循环

简单实现：连续失败 3 次 → 跳过压缩，让用户手动 `/clear`。

## 最终设计

```
should_compress(messages):
    estimated_tokens = sum(len(str(m)) / 4 for m in messages)
    return estimated_tokens > max_tokens * 0.75  # 75% 阈值

compress(messages):
    1. 找最后一条 user 消息的位置 → split_index
    2. Head = messages[:split_index]（旧对话）
    3. Tail = messages[split_index:]（当前轮，保留）
    4. 调 LLM 把 Head 总结成一段摘要
    5. 可选：把摘要写入 MEMORY.md（借鉴 OpenCLAW 的压缩前刷新）
    6. 返回 [摘要消息] + Tail

agent run loop 中：
    if should_compress(self.messages):
        self.messages = await compress(self.messages)
        yield {"type": "compacted"}
    # 继续正常循环
```

### 关键参数

| 参数 | 值 | 来源 |
|------|-----|------|
| 触发阈值 | 75% | 比 tinypace 的 92% 更保守，给当前轮留更多空间 |
| 摘要模型 | 用主模型（DeepSeek） | 不引入额外模型依赖 |
| 摘要最大 token | 1000 | 压缩后的摘要不应太长 |
| 熔断上限 | 连续 3 次 | 参考 CC |
| Token 估算 | `len(str) / 4` | 中文约 1.5 字/token，英文约 4 字/token，取 4 偏保守 |

### 为什么是 75% 而不是 tinypace 的 92%？

tinypace 的 92% 阈值配合了两阶段压缩 + 文件恢复 + 截断 fallback 等一整套机制。我们只有一个简化的 LLM 摘要，所以留更多缓冲空间（75% = 还有 25% 空间接收新消息）。
