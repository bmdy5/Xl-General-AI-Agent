# 阶段 1：核心循环与基础工具

> 老肖 | 2026-05-09

目标：跑通 Agent 最核心的循环——**用户输入 → LLM 调用 → 解析 tool_calls → 执行工具 → 把结果喂回去 → 循环直到没有 tool_calls**。

验收标准：能对话、能读文件、能写文件、能执行 shell 命令。

---

## 1. 技术选型

### 1.1 核心循环用什么模式？

四个框架有三种写法：

| 模式 | 代表 | 代码 |
|------|------|------|
| **while-true + AsyncGenerator** | CC | `while(true) { callModel(); if(!tool_calls) break; runTools(); }` |
| **递归 async generator** | tinypace | `query()` 里 `yield` 完消息后递归调用自己 |
| **同步状态机** | hermes | `while + if/else`，同步执行，不支持流式输出 |

我选了 **while-true + AsyncGenerator（CC 模式）**。原因：

- **最直观**——"一直调模型直到它不调工具为止"，心智模型就是 while-true
- **状态显式**——每轮重建 state，调试时打印 turn number 和 messages 长度就能定位问题
- **流式输出免费**——async generator 天然支持逐字输出
- **CC 生产验证过**——这个模式在全世界最大的 Agent 产品上跑了几年

tinypace 的递归模式更优雅但调 bug 时看调用栈会晕——递归嵌套 5 层你得从最深处一层层往外扒。等以后重构时再考虑。

### 1.2 LLM 接口用什么？

直接用 **LiteLLM**（tinypace 用的就是这个）。统一了 Anthropic/OpenAI/DeepSeek 等所有 provider 的接口，换模型只改一行配置。

```python
# 换模型只需改 model 参数
LLMClient(model="deepseek/deepseek-chat")     # 我现在用的
LLMClient(model="openai/gpt-4o")              # 随时可换
LLMClient(model="anthropic/claude-sonnet-4-6") # 随时可换
```

### 1.3 工具系统怎么设计？

结论：**抄 tinypace 的 BaseTool ABC + 抄 hermes 的 ToolRegistry 单例**。

看对比文档里的原话：

> tinypace 的 `base_tool.py` — **推荐首选**——BaseTool ABC，接口最干净
> hermes 的 `registry.py` — ToolRegistry 单例，register/deregister/get_definitions

tinypace 没有中心化 Registry（按需动态收集），hermes 每个工具文件自己注册。简单场景下 hermes 的 register 模式更直接。

## 2. 抄了哪些代码

### 2.1 `base_tool.py` — 直接抄 tinypace（102 行 → 80 行）

**来源**：`tinypace-ai-agent/src/agent/tools/base_tool.py`

**抄了什么**：
- `BaseTool` ABC：`name`、`description()`、`is_read_only()`、`is_concurrency_safe()`、`needs_permissions()`、`get_tool_definition()`、`validate_input()`、`call()`
- `ToolResult` dataclass：`type`（result/progress）、`data`、`result_for_assistant`
- Fail-Closed 默认值：`is_concurrency_safe()` 默认 False

**改了什么**：
- 去掉了 pydantic 依赖——`ToolResult` 从 `BaseModel` 改成 `dataclass`，少一个依赖
- 去掉了 `execute()` 方法——核心循环直接用 `call()` 的 async generator

**为什么抄这个而不是 openclaw 的 ToolDescriptor？**

openclaw 的 `ToolDescriptor` 是一个 TypeScript 联合类型，区分 core/plugin/channel/mcp 四种来源。但我现在就 3 个工具，不需要这些分类。等工具多到需要按来源管理时再考虑。

### 2.2 `registry.py` — 简化自 hermes（538 行 → 60 行）

**来源**：`hermes-agent/tools/registry.py`

**抄了什么**：
- `ToolRegistry` 单例模式
- `register(deregister/get/get_definitions/dispatch` 核心方法
- 模块级单例：`registry = ToolRegistry()`

**去掉的**（hermes 原版这些对单用户 agent 是过度设计）：
- TTL 缓存（`_CHECK_FN_TTL_SECONDS = 30.0`）——hermes 是长时间运行的服务进程，需要缓存 tool check_fn。我的是 CLI，每次启动重新注册，不需要
- 线程安全（`threading.RLock`）——单用户、单线程，没有并发注册的问题
- toolset 管理——hermes 按 terminal/browser/search 分组管理工具。我目前 3 个工具不需要分组
- `_generation` 计数器——给外部做 memoize 用的，我的 registry 不会在运行时变化
- `discover_builtin_tools()` ——AST 扫描自动导入，我手动注册更直观

**为什么简化而不是直接 import？**

hermes 的 registry.py 是一个完整的企业级实现，538 行处理了各种边界情况。但对我而言，60 行就能搞定的事情导入 538 行就是给自己找麻烦。Anthropic 说了"简单优先"。

### 2.3 `session/handler.py` — 简化自 tinypace（269 行 → 80 行）

**来源**：`tinypace-ai-agent/src/agent/session_handler.py`

**抄了什么**：
- JSONL 增量追加（一行一条 JSON，只追加不修改）
- `os.fsync` 强制刷盘（crash-safe）
- 备份轮换（`.jsonl.bak`）

**去掉的**：
- LangChain 消息序列化——我的消息就是 `dict`，不需要来回转换
- `load_messages_by_range()`——给 memory_search 用的，阶段 4 才需要
- `_get_default_storage_dir()` 里的平台判断——macOS 就一种路径

对比文档里说：

> JSONL 增量追加 >> JSON 全量读写（tinypace 的做法）

这是关键设计——每次追加一行，而不是每次改了全文重写。崩溃最多丢最后一条消息。

### 2.4 `memory/manager.py` — CC 模式，纯手写（80 行）

**来源**：Claude Code Auto Memory 分析文档 + hermes `memory_tool.py`

这是唯一没直接抄源码的模块——因为 CC 是 TypeScript，hermes 的 `memory_tool.py` 耦合了大量安全扫描逻辑（prompt injection 检测、文件锁、原子替换），对我太复杂。

但设计理念完全抄 CC：

```
写入：两步法——先写 topic 文件 → 再在 MEMORY.md 里加一行索引
检索：扫描 MEMORY.md → 注入 system prompt
注入上限：25KB（和 CC 一样）
```

## 3. 自己写的最核心代码

### 3.1 `core.py` — Agent 主循环（~200 行）

这是唯一大量手写的模块。原因很简单——tinypace 的 `query_generator.py` 有 1464 行，耦合了多平台检测、RAG 工具检索、Skill 注入、场景切换等业务逻辑。核心循环本身只占 ~200 行，不值得从 1464 行里提取。

核心逻辑：

```python
while turn < max_turns:
    # 1. 组装 system prompt（base + 记忆注入）
    system_prompt = await self._build_system_prompt()

    # 2. 调 LLM
    tools = self.registry.get_definitions()
    response = await self.llm.chat(messages, system_prompt, tools)

    # 3. 追加 assistant 消息
    self.messages.append(assistant_msg)

    # 4. 流式输出文本
    yield {"type": "text_delta", "content": response["content"]}

    # 5. 无工具调用 → 结束
    if not response["tool_calls"]:
        yield {"type": "completed"}
        return

    # 6. 执行工具，结果追加到历史
    for tc in response["tool_calls"]:
        result = await self.registry.dispatch(name, args)
        self.messages.append({"role": "tool", ...})
        yield {"type": "tool_result", ...}

    turn += 1
```

设计要点（都来自对 CC/tinypace 对比分析的理解）：

- **不可变参数 + 可变状态**：`system_prompt`、`max_turns` 全程不变（params），`messages` 每轮追加（state）。CC 就是这么分的
- **模型驱动退出**：不是用户说"结束"才停，是模型不调工具了才停。这就是 Anthopic 说的"Agent 自主循环"
- **每条消息都立即持久化**：用户消息存、assistant 消息存、tool result 也存。和 tinypace 一样，不做批量刷新

### 3.2 `llm.py` — LiteLLM 封装（~100 行）

tinypace 的 LLM 调用逻辑分散在 `query_generator._query_llm()` 里，和 RAG 检索、platform 检测、tool filtering 混在一起。我把它抽成独立类，只做两件事：`chat()` 和 `chat_stream()`。

## 4. 内置工具

三个基础工具，覆盖文件系统的读、写、执行：

| 工具 | 来源 | 只读 | 需审批 | 设计要点 |
|------|------|------|--------|---------|
| `read_file` | 参考 tinypace file_operations | ✅ | ❌ | 强制绝对路径（ACI Poka-yoke），100KB 截断 |
| `write_file` | 参考 tinypace file_operations | ❌ | ✅ | 强制绝对路径，自动创建父目录 |
| `bash` | 参考 CC BashTool | ❌ | ✅ | 60s 超时，50KB 输出截断 |

ACI 原则中的 **Poka-yoke** 体现：

> 强制绝对路径。SWE-bench Agent 的经验——用相对路径模型会出错，改成绝对路径后就再也没错过了。

## 6. 学到了什么

1. **先看文档再做决策，少走很多弯路**。如果没有之前那 50 篇分析文档搞懂各框架的差异，我大概率会直接抄 tinypace 的递归模式，然后在调 bug 时后悔
2. **抄代码不是复制粘贴**。hermes 的 registry.py 538 行，我只抄了 60 行——剩下的 478 行是给多线程、长时间运行、多 toolset 场景用的，我都不需要
3. **Anthropic 说的是对的**——简单优先。核心循环 200 行代码就能跑，根本不需要框架
4. **LiteLLM 是真香**。换模型改一行配置，不用为每个 provider 写一套调用逻辑
