## 2. 每个 Layer 抄了谁

### Layer 1: 压缩漏斗 — 抄 CC

| 机制 | 来源 | 一句话 |
|------|------|--------|
| SM 直挂 | CC | Session Memory 已写好了 → 直接拿来当摘要，零 token |
| 图片/附件剥离 | CC | 压缩前先拆掉，压缩后再塞回去 |
| 工具输出截断 | CC + hermes | >500 字符的工具结果截断 |
| 断点保护 | CC | 绝不从 tool_use 和 tool_result 中间切断 |
| 熔断器 | CC | 连续3次压缩失败 → 本会话不再尝试 |
| PTL 剥洋葱 | CC | 压缩请求本身也超限 → 再剥 20% 最老消息 |

### Layer 2: KI 蒸馏 — 抄 hermes + tinypace

| 机制 | 来源 | 一句话 |
|------|------|--------|
| 结构化模板 | hermes | 不是随意摘要，强制输出：任务/约束/已完成/当前状态/堵塞项/关键决策 |
| 双阶段压缩 | tinypace | Phase1 压旧历史 → 还不够 → Phase2 压当前轮 |
| 迭代合并 | hermes | 新旧摘要融合为一份，永远不堆积 |
| Strategy B | tinypace | 只保留最新摘要，旧知识通过 search_memory 访问 |
| Periodic Nudge | hermes | 每 N 轮推动 agent："有没有值得存的知识？" |

### Layer 3: 向量库存储 — 抄 openclaw + tinypace

| 机制 | 来源 | 一句话 |
|------|------|--------|
| 混合索引 | openclaw | BM25（精确匹配文件名/函数名）+ 向量（语义匹配） |
| Parent-Child | tinypace | 索引存摘要（Parent），检索时通过 index range 读 JSONL 原文（Child） |
| 日期文件 | openclaw | `memory/YYYY-MM-DD.md` 日记式记录 |
| 版本计数器 | tinypace | `compression_count` 单调递增 |
| Fallback | openclaw | 主后端挂了 → 懒加载内置后端 → 下次请求尝试恢复 |
| 硬上限 | openclaw | `maxInjectedChars=4000`，记忆再多也不撑爆上下文 |

### Layer 4: 动态注入 — 抄 openclaw + CC + tinypace

| 机制 | 来源 | 一句话 |
|------|------|--------|
| 强制召回 | openclaw | 工具描述写 "Mandatory recall step"，模型必须先搜记忆 |
| XML 隔离 | tinypace | `<memory_block>` 标签，记忆不和对话消息混在一起 |
| 构造时固定 | CC | 记忆在 system prompt 构造时注入，不是中途动态塞 |
| 窗口预检 | openclaw | 可用 token < 16000 → 直接拒绝，不浪费 API 调用 |
| 状态复灌 | CC | 压缩后重新注入当前打开的文件、Plan、工具声明 |
| Transcript 修复 | openclaw | 消息修改后修孤儿 toolResult、补缺失配对 |

## 3. 时间戳 + 最新优先怎么做

这是我们在讨论中注意到但还没设计的部分。文档里有三个现成的模式：

```
1. tinypace compression_count（单调版本号）
   → 每次压缩 +1，新 KI 版本号更高
   → 检索时同主题 KI 取版本号最大的

2. openclaw YYYY-MM-DD.md（日期文件）
   → 同一天的知识存在同一个文件
   → 日期越新权重越高

3. hermes 迭代合并（merge, not stack）
   → 新旧知识融合，不是叠加
   → "用户喜欢 A" → 后来"用户喜欢 B"
   → 合并后只保留"用户喜欢 B"
```

组合使用：
```
检索到同主题的多条 KI →
  按时间戳排序 →
  取最新的 →
  如果有冲突，最新优先 →
  旧 KI 标记为 stale（不删除，但权重降低）
```

## 4. 对我们的 agent 意味着什么

### 我们已有的

| 已有 | 对应 Layer |
|------|-----------|
| save_memory 工具 + 5类分类 | Layer 2 的基础 |
| MEMORY.md 索引 | Layer 3 的简化版 |
| system prompt 注入 | Layer 4 的基础 |

### 还没做的（按优先级）

| 优先级 | 功能 | 抄谁 | 复杂度 |
|--------|------|------|--------|
| **P0** | 上下文压缩（Layer 1） | CC 漏斗 + tinypace 双阶段 | 中 |
| **P1** | 时间戳 + 最新优先 | openclaw 日期 + tinypace 版本号 | 低 |
| **P2** | Periodic Nudge | hermes | 低 |
| **P3** | 向量库存储 | openclaw BM25 + tinypace 向量 | 高（需 embedding） |
| **P3** | 强制召回步骤 | openclaw Mandatory recall | 低 |

### 当前最该做的是 P0 + P1

没有压缩（P0），记忆再多也会被上下文窗口限制。
没有时间戳（P1），旧知识会覆盖新知识。

向量库（P3）是以后的事——先让 agent 能正确压缩 + 正确记忆，再考虑向量检索。

## 5. 你朋友的设计价值在哪

他把四家的设计从"纸上分析"变成了"能跑的系统"。对我们最有价值的三点：

1. **KI 比 Skill 更适合通用 agent**。Skill 是一个完整的流程（"部署"），KI 是一个独立的知识单元（"部署时的 SSH 端口是 2222"）。KI 更细粒度，更容易复用。

2. **时间戳解决"记忆腐败"问题**。我们之前的计划只考虑了"怎么存"，没考虑"存错了怎么纠正"。时间戳 + 最新优先 = 自动纠错。

3. **向量库不是必须的，但标记了方向**。目前 MEMORY.md 够用，但 KI 蒸馏量大后必然需要语义检索。他提前占了这个位置。
